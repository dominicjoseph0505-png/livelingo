1. What LiveLingo should become
LiveLingo is a language-bridging communication app with two separate modes: (A) Face-to-Face Translator for people standing together, with ongoing listen → translate → speak; (B) Live Translation Call for two people joining an in-app voice/video meeting from separate devices. Both modes use the same six-language system and must translate in both directions.
Languages: English (en), Kannada (kn), Hindi (hi), Spanish (es), German (de), and Tamil (ta). Keep language codes in one shared registry. The app must use the selected source and target language in the actual speech-recognition, translation, and voice-generation services—not only in the UI.
2. Two-mode split UI
Mode A — Face-to-Face Translator
A large, clear two-sided layout: 'You speak' language on one side and 'They hear' language on the other.
Start/Stop Listening, swap languages, mute playback, and clear transcript controls.
Continuous or turn-based listening with visible states: Listening, Translating, Speaking, Paused, and Error.
Support one shared device first. If the phone speaker is used, prevent generated translation audio from being re-captured as source speech; use headphones or push-to-talk as a fallback when echo cancellation is insufficient.
Show original text and translated text separately. Never pretend a translation is complete while the provider is still processing.
Mode B — Live Translation Call
Create/Join Call using an invite link or room code; each participant selects the language they speak and the language they want to hear.
Build a clean meeting-style screen with participant tiles, mic/camera controls if video is implemented, connection quality, captions/transcripts, and End Call.
Translate each speaker's speech into the other participant's selected language and play generated speech to the correct remote participant.
Keep translated audio out of the source transcription path. Use timestamps and cancellation to prevent delayed audio from playing over a newer utterance.
Prioritize low perceived delay: stream partial STT where supported, translate short completed utterances, use streaming TTS where supported, and measure real end-to-end latency. Do not claim 'zero lag'.
3. Natural, human-like translated voice
Use high-quality neural TTS voices with natural pacing and pronunciation. Prefer streaming output, suitable voice choices for each language, and sentence-aware chunking that avoids cutting words or making every phrase sound robotic. Preserve meaning, names, and numbers. Where the provider supports it, use expressive prosody and adjustable speaking rate; do not imitate a specific real person's voice.
Verify TTS support separately for English, Kannada, Hindi, Spanish, German, and Tamil. Some providers may not offer equally natural voices for every language. If a suitable voice is unavailable, disclose the limitation and provide translated text rather than faking speech.
4. Do callers need the same Wi-Fi?
No. Callers do not normally need to be on the same Wi-Fi. Each person needs a working internet connection; one can use Wi-Fi and the other mobile data. A real-time calling service uses internet media transport (typically WebRTC with appropriate connectivity infrastructure). Network quality, latency, firewalls, and mobile signal affect call quality. The face-to-face mode can work locally on one device, but cloud speech/translation services still need internet unless offline models are deliberately implemented.
5. Suggested technical shape
Frontend: React + TypeScript + Vite; responsive UI with two clearly separated mode cards.
Calling: maintained WebRTC platform such as LiveKit for real in-app calls; first prove ordinary two-person audio works.
Backend: secure API for short-lived call tokens and server-side STT/translation/TTS provider requests.
Pipeline: source audio → STT with source locale → translation to listener locale → natural TTS → playback only to the intended listener.
Language registry: en, kn, hi, es, de, ta; track verified STT, translation, TTS voice, and provider limitations separately.
Security: provider keys only on the server; use environment variables, validation, rate limits, safe logs, and cleanup.
Vercel: use it for the frontend when ready. A persistent real-time media server or long-running streaming pipeline may need a separate hosted service; do not assume Vercel serverless functions alone can host the entire call stack.
